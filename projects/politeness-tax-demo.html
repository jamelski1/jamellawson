Break the Benchmark Yourself

This page runs the Politeness Tax study's actual extractor code, unmodified, in your own browser. Pick a recorded model reply, run both extractors on it, and watch one ruler call a correct answer wrong while the other passes it. Nothing is sent to a server, and no model is called.

The full study result

The study recorded 1,336 replies: 167 LiveCodeBench problems, each answered by GPT-5.4 and Claude Opus 4.6 under four prompt registers that differ only in how the question is framed. The tables below are the full study's numbers, recomputed in the study's demonstration notebook. The interactive section further down works on a smaller bundled subset, labeled there.

RegisterNaive extractor pass rateRobust extractor (Sieve) pass rate
Terse73.4%81.7%
Casual65.9%81.1%
Detailed (polite)57.2%81.1%
Multilingual65.6%84.1%

Same 1,336 replies, scored two ways. Under the naive extractor, terse beats detailed by 16.2 points (paired McNemar test, p about 1.1×10-7). Under the robust extractor the gap is 0.6 points (p = 0.85), which is no effect. The paper reports 15.9 points (p = 1.6×10-7) and 0.0 points (p = 1.00) for the same comparison from its three extractor run; the small differences come from which extractor run is tabulated, and both tell the same story.

The gap exists before a single test runs. Polite prompts make models explain themselves after the code, and the naive extractor hands that trailing explanation to the interpreter along with the code. Its failures are syntax errors on answers that were often correct.

What this page is, and what it is not

            
This page bundles a subset of the study's 1,336 recorded replies: eight problems, each with all eight of its replies (two models times four registers). The worked example from the study is always included. The next four problems are the ones with the most naive extractor failures across their eight replies, so the failure mode is easy to find. One problem is included where several replies genuinely failed even under the robust extractor, so real model failures are represented too. The last two are problems where the naive extractor compiled every reply and most replies passed, so visitors can also see the two extractors agree. Ties are broken by problem id.

            
The pass and fail outcomes shown for each reply are the study's recorded outcomes. During the study, each Sieve extraction was graded against its problem's full LiveCodeBench test suite. The naive outcome is derived, the same way the study's notebook derives it: an extraction that does not compile was certainly scored wrong, and an extraction that compiles is byte for byte the same code Sieve produced in 1,067 of 1,068 cases across the full study, so it inherits Sieve's verdict.

            
This page does not regrade replies against the full test suites, because the complete LiveCodeBench tests are access gated and cannot be redistributed. That is also why the try your own box stops at extraction and a compile check: grading needs the benchmark's tests for the problem, and those are not ours to ship.

            
The extraction and compile checks, by contrast, really do run here. The Python runtime (Pyodide, Python compiled to WebAssembly) executes the study code inside your browser, on your machine. If the runtime cannot load, the page falls back to compile results precomputed with the identical code, and says so.

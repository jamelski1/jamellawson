Under Review at SANER 2027

Beyond Text Only Estimation

How long will a software issue take to fix? This project tests whether a model can predict implementation effort from the words of an issue report alone, and whether adding the repository’s own history makes the prediction any better. The paper, “Predicting Software Maintenance Effort: An Empirical Study of Five Open-Source Repositories,” is under review at SANER 2027 in the RENE Track.

What it is

Software teams plan around effort estimates, and most estimation research reads only the text of a task: its title, its description, maybe its discussion. That ignores everything the repository itself knows, such as which files churn, how old they are, and how often they change. Beyond Text Only Estimation, or BTOE, replicates and extends the SE3M study of Ribeiro and colleagues, which estimated effort from pre-trained text embeddings, and asks a second question the original did not: does repository history add anything the text does not already carry?

How it works

The pipeline mines issue and pull request pairs from large open source projects, where the time between an issue opening and its linked pull request merging gives a measured duration to predict. The final dataset is drawn from five large open source repositories, with durations between one hour and ninety days. A held-out test set of 896 pairs is used for every comparison.

Three XGBoost estimators are trained on different views of the same issues:

  • Model A, text only. CodeBERT embeddings of the issue text plus text features such as word count. This is the SE3M replication baseline.
  • Model B, repository only. Structural features mined from the repository with PyDriller, including change frequency, churn per file, and average file age.
  • Model C, combined. Both feature sets together, the direct test of whether repository history improves on text alone.

Models are compared with Standardized Accuracy, mean and median absolute error, and paired Wilcoxon signed-rank tests with effect sizes, because effort data is heavily skewed and squared-error metrics mislead on it. The repository also includes a small Flask web app, the Issue Duration Estimator, that returns predictions from all three models for a new issue title and description.

Primary model comparison from the project results. Standardized Accuracy measures improvement over random guessing on absolute error and is the primary metric throughout.

The honest headline is a negative result. Text alone carries a modest but real signal. The combined model scores slightly higher than text only, but the difference is not statistically significant (p = 0.225) and the effect size is negligible, and that pattern holds across sensitivity checks at five duration thresholds. Repository features alone are weaker still: Model B largely collapsed, predicting the three to seven day bucket for 97 percent of test cases regardless of the actual duration.

Two further results explain why. The single most predictive feature in the text model is word count, a rough proxy for task complexity, and an encoder ablation swapping CodeBERT for UnixCoder and for the general purpose BGE embedding model lands every encoder within a 15.8 to 16.1 percent Standardized Accuracy band. The signal the models find is mostly general properties of the writing, not code semantics and not repository structure. For practitioners, that is a useful caution: fusing more data sources into an effort estimator does not help if the added sources carry no signal of their own.

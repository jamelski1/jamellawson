Under Review at FORGE 2027

The Politeness Tax

Does polite phrasing make a language model write worse code? This study shows that a widely used style of evaluation pipeline can manufacture that effect without any change in model behavior. The full paper, titled “The Politeness Tax Is a Measurement Artifact: Prompt Register Effects as Code Extraction Confounds,” is under review at FORGE 2027 in the Data and Benchmarking Track.

What it is

The project began as a benchmark of how the politeness of a prompt changes large language model output quality, consistency, and cost, built on HumanEval coding tasks with a Python evaluation pipeline. While chasing an anomaly in that pipeline, where a solution that passed in a chat interface failed consistently through the API harness, the study turned into an audit of the scoring apparatus itself: the code extractor that pulls a program out of a model reply before the tests run.

The finding is that the extractor is part of the benchmark. Scored one way, polite prompts appear to cost a capable model roughly one problem in six. Scored with extractors that handle real model output carefully, the same replies show no politeness effect at all.

How the study works

The experiment uses 167 LiveCodeBench problems with contest dates on or after August 1, 2024. Each problem statement appears word for word inside one of four fixed wrappers that differ only in register: a terse agent style note, a casual message to a teammate, a polite and detailed chat request, and a Chinese language wrapper reported as a robustness aside. Two frontier chat models, GPT-5.4 and Claude Opus 4.6, answered every problem once per condition, giving 334 paired observations per condition and 1,336 completions in total.

Every completion was scored against the full official test suite for its problem, with 33 to 44 tests per problem and no test sampling. Conditions were compared problem by problem with exact McNemar tests, so each problem serves as its own control. The same stored completions were then scored four ways: with a standard but naive extractor, with a robust multi-candidate extractor built for the study, with EvalPlus sanitize, an independent extraction routine from the EvalPlus project, and with LiveCodeBench’s own fence-only extractor. No model was ever re-queried, so every difference between scorers reflects scoring alone.

What it found

Under the naive extractor, terse prompts passed 73.4 percent of problems and polite, detailed prompts passed 57.5 percent, a paired difference of 15.9 points that is highly statistically significant. Both robust extractors erase the effect on the identical replies, and LiveCodeBench’s own extractor reverses it, reporting a politeness bonus of about 12 points, because it only accepts code inside markdown fences and the polite replies fence their code more often.

Pass rates on the full official test suites for the same 1,336 completions, scored three ways. Absolute levels differ by extractor design; the comparison that matters is the gap between conditions.

The mechanism is mechanical. Polite prompts make models explain themselves after the code. The share of replies carrying more than 20 characters of non-code text rises from 29.6 percent for terse prompts to 58.1 percent for detailed ones, and the naive extractor feeds that trailing prose to the interpreter along with the code. All 268 of its compile failures were syntax errors on otherwise recoverable answers. The gap is visible before a single test runs: the naive compile rate falls from 88.0 percent on terse prompts to 73.4 percent on detailed ones, while the robust extractor compiles 100 percent of replies in every condition.

The paper also catalogs fifteen pipeline pitfalls encountered in this one study, each mapped to the wrong conclusion it produces, and proposes a cheap diagnostic for benchmark papers: report the extraction rate by condition alongside pass rates, so a scoring artifact is not mistaken for a model behavior.
